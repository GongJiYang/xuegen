## 1. 两条写课程页的路统一（Functional Core, Imperative Shell）

**要防什么**：课程页是唯一的进度来源。任何写入都要满足三件事：写之前检查过、要么全写要么不写、写完能撤回。现在课程会话的 `course_close` 三条都满足；总控的 `course_plan` 是「解锁 → 编辑工具直接改 → 上锁」，**三条都不满足**。

**取**：
- 核心与外壳分开：「这次改动对不对、改哪些文件」是不碰磁盘的纯逻辑（`planCheck`、`checkCoursePage` 已经是）；「暂存、落盘、jj」是外壳，只有一份。
- 两个工具只是**两个按角色开的门**，后面是**同一台事务机**。

**舍**：
- 不追求「全部函数式」。落盘、fsync、rename、jj 天生是命令式的，留在外壳里，写薄就好。
- 不为总控另造一套事务。

**做法**：
- `course-close.mjs` 的 `stage` 支持总控：总控可以 stage 任何一门课；加 `--new <slug>` 用于新建课程（暂存里没有基线文件，check 校验它是合格的新课程页）。
- 加 `plan` 动作：和 `shift` 一样，在暂存副本上跑 `course-schedule.mjs plan --write`，再 check → commit。
- 提交名按事情分：收课 / 存档点 / 顺延 / **计划**（新）。`undo` 仍只撤「收课」；「计划」以后要撤回时，加一个 `undo --label 计划`。
- `course_plan` 收缩为总控入口：`stage`（含 `--new`）/ `plan` / `check` / `commit` / `abort` / `board`，**去掉 `unlock`、`lock`**。guard 里总控对 `wiki/courses/` 的编辑工具直写权限同时收回，只能写暂存。
- 结果：库里课程页只有一条写入路径，所有写入都有检查、都原子、都记 jj。

## 2. 模块怎么拆（深模块，按隐藏的信息拆）

**要防什么**：改一处要读懂一大片；同一个知识（比如 jj 文件名怎么转义）散在多处，改漏一处就出错。

**取**：
- 模块的价值 = 它藏起来的复杂度 ÷ 接口大小。按「这个模块独占哪条知识」拆，每块接口尽量小。
- 300 行是**警惕信号**，不是硬目标。

**舍**：
- 不为凑行数拆。数据表（`strings.ts`）、协议类型（`protocol.ts`、`data-protocol.ts`）、皮肤契约（`contract.ts`）长一点没关系，拆开反而要在几个文件之间跳。
- 不拆出只被调用一次、只有三行的「浅函数」。

**做法**：
- `course-close.mjs`（1138 行）按它藏的五条知识拆：
  | 模块 | 独占的知识 | 对外接口 |
  |---|---|---|
  | `close/rules.mjs`（纯） | 课程页、概念页、log、index 的规则；归属判断 | `planCheck(manifest, staged, current)`、`isOwned` |
  | `close/staging.mjs` | 暂存目录布局、manifest、写时复制 | `stage`、`loadManifest`、`walkStaged` |
  | `close/durable.mjs` | 原子落盘、journal、崩溃恢复、只读锁 | `applyChanges(vault, changes)`、`recover(workspace)` |
  | `close/jj.mjs` | jj fileset 转义、提交、diff 解析、可达性 | `commit(vault, msg, paths)`、`diffEntries`、`laterChanges` |
  | `course-close.mjs` | 命令行与各动作的编排 | CLI |
  现有 57 条测试不改断言，拆完全过才算完。
- `bookshelf.mjs`（1039 行）、`reading-queue.mjs`（753 行）、`cycle.mjs`（660 行）先只**看**：列出它们各自藏的知识。有两块以上互不相干的才拆，否则留着，写进 AGENTS.md 的例外清单。
- `AGENTS.md` 的 300 行规则改成：「超过 300 行要在文件头说明为什么不拆（例如数据表、协议类型），或者按隐藏的信息拆开」。

## 3. 改名过渡怎么收尾（Parallel Change）

**要防什么**：新旧两套名字长期并存。每条规则都要写两遍，测试也要测两遍；迁完了却不删旧名，比改名之前更乱。

**取**：三步走——扩展（新旧都认）→ 迁移（调用方和数据换成新名）→ 收缩（删旧名）。**收缩要排日期**，不能一直拖。

**舍**：不搞「先删旧再改数据」的一步到位，那样真实库在中间状态会断。

**做法**（对应发版）：
- **扩展**：已完成。阶段 1 的代码新旧布局都认，`rename-vault.mjs`、`vault-lint.mjs` 已就绪。
- **迁移**：0.8.0 装好后立刻照 `RENAME-DAY.md` 改真实库，需要用户在场并同意。
- **收缩**：迁移验收通过后的**下一个版本（0.9.0）**删掉旧名代码。清单从 `grep` 得出：
  - `vault-paths.ts` 的 `both(...)`（7 处）；
  - 5 个 SKILL.md 里的「旧库：…」；
  - `boardPaths` 的旧位置；
  - 测试里的旧布局用例。
  删完之后 `rulePaths` 每个键只剩一个路径。

## 4. 技能手册前后不一致（Skill 编写最佳实践）

**要防什么**：模型照着有矛盾的手册做事，就会自己挑一种，甚至发明第三种（11-10 手改排期日期就是一例）。

**取**：
- 同一件事只留**一个说法、一个命令**。
- 容易出错的步骤写死，自由度越低越好；能交给脚本的就交给脚本（收课、顺延已经是工具动作）。
- 「做 → 检查 → 改 → 再检查」的闭环写清楚。
- 正文保持精炼，细节放进 `references/`，用到时再读。

**舍**：
- 不把整份 SKILL.md 从代码生成。技能是写给模型看的散文，生成出来会变成说明书腔。
- 只让**步骤编号表**有唯一来源。

**做法**：
- 修 `FEATURE-WIKI.md` 末尾列的 6 处不一致：
  - 讲后读只留一个命令（`bookshelf.mjs lecture`；主项通读已经搬进书房）；
  - 收课截图的编号改成和执行顺序一致；
  - 周核实写明经 `course_close`；
  - SKELETON 1.3 改成 cycle-plan；
  - 改计划单独成一节（改完第 1 条之后，它就是「`course_plan` stage → plan → commit」）。
- 固定流程（开课、收课、顺延、撤销、存档点）的步骤编号只写在 SKILL.md 一处。`FEATURE-WIKI.md` 的步骤部分改由脚本 `scripts/feature-wiki.mjs` 从 SKILL.md 抽取生成，`lint:skills` 检查两边一致。以后界面「第 3/8 步」也读同一份。
- `lint:skills` 加两条检查：同一个脚本命令不能在两个技能里写成不同的参数；SKILL.md 里不能出现「旧库：」（这一条在第 3 条收缩时打开）。

## 5. 版本怎么小步发出去（Trunk-Based + Keep a Changelog + SemVer）

**要防什么**：开发版和装的版本差得越远，一次换上的东西越多，出了问题越难判断是哪一处。

**取**：
- 小步、频繁地合进主干并发版。
- 每个版本有一份人能看懂的变更记录。
- 版本号表达影响：0.x 阶段，加功能升次版本号，只修 bug 升修订号。

**舍**：
- 单人项目不需要严格的「无分支」。`desktop` 分支保持短命就行：每次发版快进合进 `main`。
- 不为没做完的功能开长期分支；没做完的功能用开关先关着（比如 `XUEGEN_SANDBOX=off`）。

**做法**：
- **0.8.0 = 阶段 1–4a**：卡片直连、新旧库布局都认、权限门卫、收课事务、`course_plan`、系统沙盒，再加上今天的 Bear 小改。
  - 发版前：清掉 `guard/path.test.ts` 里的个人路径；`CHANGELOG.md` 按 Keep a Changelog 写一个 `[0.8.0]` 段（新增 / 变更 / 修复 / 安全）；照 `RELEASE.md` 打包；请用户自己退出学根再替换。
  - 发版后马上做 RENAME-DAY（第 3 条的迁移）。
- **0.8.x**：第 1、2、4 条整理，每条做完就发一个修订版或次版本，不攒着。
- **0.9.0**：第 3 条收缩（删旧名）。
- 以后的节奏：一个阶段或一个整理条目做完就发版。`CHANGELOG.md` 常驻 `[Unreleased]` 段，每个批次合入时顺手写一行。
