# 文章知识架构

目标：只建立一篇文章所需的知识结构，不代写正文，不替用户展开例子、证明、计算或修辞。

## 触发与范围

1. 用户说“整理今天学的内容”“做成文章结构”“抽象成知识架构”“告诉我每个知识点的精准抽象”等时使用。
2. 默认范围是当前会话中今天已经讨论的内容；如果用户指定主题、时间或材料，遵从指定范围。
3. 只使用实际对话、实际读取的文件和实际执行的结果。没有来源的内容标记为“待核实”，不补造事实。
4. 不自动写入 Wiki、notes 或文章文件。用户明确要求保存时，才按目标位置写入；默认先在回复中给出结构。

## 核心原则

- 输出知识地图，不输出成文稿。
- 每个知识点必须能用一句话精确定义；避免“很重要”“进一步理解”等空泛标签。
- 区分定义、前提、机制、结论、边界、证据和开放问题。
- 不把例子当作定义，不把经验规律写成普遍规律。
- 不根据内容多少强行增加层级；没有依据就不创建节点。
- 保留用户的疑问、错误和未验证项，但不要改写成已经解决的结论。

## 抽象流程

1. 提取主题、用户目标和已确认事实。
2. 识别文章的中心问题：读者最终需要理解什么关系或判断什么问题？
3. 把内容拆成最小可定义的知识点。
4. 为知识点建立父子关系、依赖关系、因果关系、对比关系和应用关系。
5. 为每个知识点标出前提、边界和证据状态。
6. 按“先决概念 → 核心机制 → 推论/判断 → 边界与开放问题”排序。
7. 最后检查：是否有循环依赖、未定义术语、把例子当结论、把推测当事实。

## 输出格式

默认使用以下结构，不写长段落：

```markdown

## 1. 中心问题
- 问题：
- 目标判断：
- 文章主张：

## 2. 知识层级

### 2.1 基础定义
- **知识点**：一句精准定义。
  - 角色：定义 / 前提 / 机制 / 结论 / 边界 / 证据
  - 依赖：需要先理解的知识点
  - 区分：最容易混淆的相邻概念

### 2.2 核心机制
- **知识点**：一句精准定义。
  - 输入 → 过程 → 输出：只写抽象关系，不展开细节
  - 依赖：
  - 适用条件：

### 2.3 推论与判断
- **知识点**：从哪些前提得到什么结论。
  - 推导状态：已核实 / 对话中推导 / 待核实
  - 可验证方式：

### 2.4 边界与反例方向
- **边界**：结论在哪些条件下不成立或需要修改。
- **未解决问题**：

## 3. 关系图

```text
基础定义 → 核心机制 → 推论/判断
       └→ 对比概念
核心机制 → 适用边界 → 开放问题
```

## 4. 精准摘要
- 一句话主张：
- 三个不可删除的知识点：
- 一个最容易误解的关系：
- 一个仍需验证的问题：
```

## 深度控制

用户只说“整理文章”时，保持抽象层级，不自动扩展。

- 概览：保留中心问题、3–7 个核心知识点和主要关系。
- 理解：补充依赖、机制、边界和验证方式。
- 深入：只有用户明确要求时，才加入公式、计算、代码实验、反例或文献证据。

“文章知识架构”不等于“文章大纲写作指导”。不要主动告诉用户如何开头、如何铺陈、如何使用比喻或如何润色；除非用户另行要求写作方法。
